WRG-OS — Blueprint Magang-Safe

Panduan orientasi ringkas untuk anak magang. Aman dibagikan.

⚠️ Versi khusus magang. Konten internal/sensitif (RACI-PDCA-KPI, CRM, HR, target finansial, keputusan direksi/ADR, security & secrets, deploy/infra) sengaja tidak dimuat. Aturan di sini adalah pagar (gate) yang ditetapkan Direktur — wajib dipatuhi.

1 · Aturan Branch (paling penting)

feature/* ──PR──▶ dev ──(hanya Direktur)──▶ main ──▶ auto-deploy prod
  • main HARAM disentuh. Terproteksi; push langsung diblokir. Promosi dev → main hanya Direktur.
  • Semua kerjaan lewat dev: branch dari dev → buka PR base dev → tunggu CI hijau → di-review → merge ke dev. Tim magang berhenti di dev.
  • Nama branch & judul PR memuat F-number (mis. feat/f210-...) — board Roadmap update otomatis.

2 · Peta Scope — Boleh vs Off-Limits

BOLEH

  • Fitur produk ber-F-number yang ditugaskan Direktur/lead — di luar 4 domain terlarang.
  • Perbaikan UI non-sensitif, widget laporan biasa.
  • Bug fix di area yang ditugaskan.
  • Menambah test, dokumentasi fitur yang dikerjakan.

OFF-LIMITS (STOP, tanya Direktur)

  • Management/managerial — permission/scope, admin, dashboard eksekutif, OKR/KPI.
  • Infrastruktur — CI/CD, deploy, docker, server, secrets, `.env`.
  • CRM — accounts/customers/deals, pipeline, mirror Accurate, kepemilikan akun.
  • HR — data karyawan, roster, HR/HRD, cuti, provisioning user.

Kalau ragu apakah suatu tugas masuk domain terlarang → anggap terlarang, tanya dulu.

Di mana daftar fitur & tugasmu?

Fitur dilacak di board WRG-OS Roadmap (item ber-F-number, status otomatis dari PR). Kamu tidak otomatis dapat akses board penuh — Direktur memberi F-number spesifik / view yang sudah difilter untuk tugasmu. Kerjakan hanya F-number yang ditugaskan; belum jelas → tanya Direktur.

3 · Gate yang wajib lolos tiap PR

Conventional Commitsfeat: / fix: / chore(scope): / docs: — menentukan versi rilis.

LegacyJangan sentuh sistem Python lama (port 8090/8091/8092) & prod/deploy.

4 · Database dummy lokal (WAJIB per fitur)

Dilarang develop/test ke DB prod. Tiap fitur pakai Postgres dummy di laptop sendiri (lihat docs/LOCAL-DEV.md).

cp .env.example .env          # set PG_PASSWORD + DATABASE_URL
docker compose up -d postgres # schema auto-apply (infra/postgres/init/*.sql)
psql "$DATABASE_URL" -f scripts/db/seed-dev.sql   # data demo (jangan copy data prod)
pnpm install && pnpm dev       # api:4000 · web:3000 · ai:8000

Verifikasi fitur jalan di DB dummy sebelum buka PR.

5 · Kalau fitur butuh perubahan / migrasi Database

1
Migrasi = file SQL BARU infra/postgres/init/NNN_*.sql (nomor tertinggi+1), additive + idempoten (IF NOT EXISTS). Jangan edit file migrasi lama. Lihat docs/MIGRATIONS.md.
2
Test migrasi di DB dummy lokal (bash scripts/db/migrate.sh), pastikan app tetap jalan.
3
WAJIB: kalau PR menambah/mengubah struktur DB → tulis section “⚠️ BUTUH MIGRASI DB” di deskripsi PR + kabari Direktur langsung. Direktur yang apply ke prod (dengan backup). Jangan pernah apply prod sendiri.

7 · Checklist sebelum buka PR

  • ☐ Branch dari dev, base PR = dev (bukan main).
  • ☐ Branch/judul memuat F-number · commit Conventional Commits.
  • ☐ Tidak menyentuh domain terlarang (kalau iya, sudah izin Direktur).
  • ☐ Diuji di DB dummy lokal · lint/typecheck/build lolos.
  • ☐ Ada perubahan DB → section “⚠️ BUTUH MIGRASI DB” + kabari Direktur.
  • ☐ Tidak ada secret ter-commit; tidak menyentuh prod/legacy 8090–8092.
